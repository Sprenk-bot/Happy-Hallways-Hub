# Hub Host development prototype

This is a separate Bun process for the early Hub Host architecture. It stores one versioned Happy Hallways account snapshot in SQLite, checks revisions before writes, and records host audit events with staff attribution. SQLite uses write-ahead logging and full synchronous writes. The default listener binds only to `127.0.0.1`.

The first production target is a school-managed Windows device. Run `bun run hub:preflight` to see which local settings are ready and which need ICT. It does not start the Host, create files, or display key contents. It checks for broad local-user ACL grants on configured files and folders, but a clear result is not proof that service-account or network-share permissions are correct. Run it under the same Windows account that will run the Host for a useful access check. It cannot verify Entra sign-in or reachability from school staff devices. `scripts/register-hub-host-task.ps1` can register a Task Scheduler startup task under a dedicated account, and `scripts/run-hub-host-task.ps1` captures its output under the ignored `.hub-data/logs` directory. These scripts have only been syntax-checked, not registered or tested under a school service account. ICT still needs to select the exact host, service identity, service supervisor, disk and folder permissions, environment configuration, and recovery procedure. Review the task in Task Scheduler after setup. The kiosk tab is not the Host process.

Run `bun run build` and then `bun run hub:host` to start the Host with the existing static app served from the same origin. The default static directory is `build`; set `HUB_STATIC_DIRECTORY` to use another built app directory. If no build exists, the Host remains API-only. The default database is `.hub-data/hub.sqlite`, which Git ignores. Set `HUB_DATABASE_PATH` to select another local file and `HUB_PORT` to change port (default `8787`). Additive schema migrations preserve the existing snapshot, revision, and checksum; v4 adds revision history, v5 adds staff-profile preferences, v6 adds separately stored concern messages and recipient read state, and v7 adds hashed kiosk activation tickets and kiosk sessions. Each upgrade creates a pre-migration copy before applying changes. Every acknowledged account revision is retained with its checksum and staff attribution in the same SQLite transaction as the live state update. TICs can stage a restore from an individual acknowledged revision between periodic snapshots. Unsupported future schema versions and damaged snapshot checksums fail closed.

LAN mode is off by default. To prepare an ICT-supervised test, set `HUB_ALLOW_LAN=true`, `HUB_HOST` to the approved bind address, `HUB_PUBLIC_HOST` to the approved DNS name, and `HUB_TLS_CERTIFICATE` / `HUB_TLS_PRIVATE_KEY` to ICT-issued PEM files. All three HTTPS values must be supplied together and the listener refuses non-loopback HTTP. Keep private keys outside the repository with Windows ACLs restricted to the service account. This configuration has not been tested on the school's LAN, and the app still needs the actual certificate, DNS, firewall and device-policy checks before multi-device use. If the school network test fails, keep LAN mode off and use the Host locally while ICT checks the network. Do not silently switch to PeerJS/WebRTC: those existing paths rely on external services and need separate approval.

## Development staff fallback

The named-profile route is disabled unless `HUB_NAMED_PROFILE_FALLBACK_ENABLED=true` is explicitly set in the Host process environment. For fictional local development only, run `bun run hub:invite:tic` to issue a one-time, ten-minute first TIC invitation, then redeem it through the page's development fallback form. The command prints the secret token once. Invitation tokens and device-session tokens are stored as SHA-256 hashes. Invitations expire after ten minutes and can be used once. Device sessions expire after 30 days and can be revoked by a TIC. The browser cookie is `HttpOnly` and `SameSite=Strict`.

This named-profile and device-enrolment route is an explicitly temporary fallback. It does **not** check a real person's identity and does **not** provide MFA. The API reports `identityVerified: false` and `mfaVerified: false`; real student data stays disallowed through this route. If ICT approves a compensating control for real use, that requires a separately reviewed implementation and configuration gate.

For the first TIC under Entra, set `HUB_BOOTSTRAP_TIC_EMAIL` to that staff member's school email and run `bun run hub:invite:tic`. The command creates an email-bound invitation that can only be redeemed through the configured Entra flow. Leave this variable empty only when creating a fictional-development fallback invitation. The bootstrap command reads the configured backup key too, so migrations it triggers can encrypt their pre-migration copy.

Microsoft Entra is the approved SSO direction. The server-side authorization-code flow uses the `@azure/msal-node` confidential client and a certificate private key. It stays disabled unless all settings are present and ICT explicitly sets `HUB_ENTRA_MFA_POLICY_CONFIRMED=true` after confirming the school tenant enforces MFA for this app. The app does not create its own MFA check or infer policy from an email address.

ICT configuration names are `HUB_ENTRA_TENANT_ID`, `HUB_ENTRA_CLIENT_ID`, `HUB_ENTRA_REDIRECT_URI`, `HUB_ENTRA_CERTIFICATE_SHA256`, and `HUB_ENTRA_PRIVATE_KEY_PATH`, alongside the MFA confirmation flag. The redirect URI must exactly match `https://<approved-host>:<port>/api/v1/auth/entra/callback`, which must be registered in Entra and served by the TLS LAN listener. Store the PEM private key outside the repository and restrict its Windows ACL to the dedicated Host service account. This configuration has not been validated against a Department tenant or school ICT policy.

The `/hub-admin` page provides the sign-in, TIC invitation, backup health and staged restore controls. An Entra first sign-in requires a TIC-issued, ten-minute invitation tied to the staff member's school email. The Host checks the returned tenant and stable Entra object ID, email-matches new profiles, and reuses the same profile on later sign-ins. TICs can link an existing fallback profile while preserving its stable staff ID and role. The invitation's role remains under TIC control. The login API reports identity and MFA as verified only when the configured Entra flow succeeds under the ICT-confirmed MFA policy. Never treat the local named-profile fallback as MFA.

## Automatic backups

The host makes an initial consistent SQLite snapshot at startup and then checks every minute for a snapshot due at the 15-minute interval. Every acknowledged state revision is also retained transactionally as a compressed SQLite revision, so a TIC can restore a specific acknowledged revision between periodic snapshots. If an off-host destination is configured, a changed revision triggers a replication checkpoint in the next one-minute backup cycle. Until that checkpoint is copied, health reports the off-host layer as degraded with pending work. The TIC view shows the measured save-to-copy lag for the latest replicated revision. The one-minute cycle is an engineering target, not a guarantee of a five-minute maximum lag. Before a supported schema upgrade, the Host first creates and verifies a separate pre-migration copy. Migration copies use the same replication queue as regular snapshots. Manifests include application/schema version, snapshot revision, top-level array counts, timestamp range where present, and a SHA-256 file checksum. The host never automatically removes a snapshot or state revision. A weekly isolated test copies the latest snapshot to a temporary database, opens it read-only, and verifies database integrity, the account checksum, and each compressed revision checksum. This checks that the file can be opened and read; a full host replacement drill remains outstanding.

The local snapshot directory defaults to `.hub-data/backups/local`; set `HUB_LOCAL_BACKUP_DIRECTORY` to change it. `HUB_OFFHOST_BACKUP_DIRECTORY` configures the preferred school-approved location. `HUB_FALLBACK_BACKUP_DIRECTORY` configures a second ICT-approved alternative. The Host copies and verifies to each configured destination, retries pending copies every minute, and reports each path separately. If the preferred location fails but the fallback works, the page reports the fallback as operational while overall protection remains degraded. `GET /api/v1/backups/health` provides TIC-only details; `/api/v1/health` reports summary status. The initial target is to copy available snapshots within five minutes. No retention duration is hard-coded and no record or backup is automatically deleted.

Set `HUB_BACKUP_ENCRYPTION_KEY_PATH` to a 32-byte random key file held outside the repository and outside the local backup folder. Backup files use AES-256-GCM; the encrypted file is authenticated before a restore is staged. Restore staging files are encrypted when a key is configured, and the temporary plaintext database used during a restore is removed after the operation. Keep the same key available to the Host and keep an independent recovery copy in an ICT-approved secure location. The current prototype supports one active key and does not rotate keys. Do not replace or delete it while any backup may need restoration. Without a key, the Host creates plaintext backup files and the TIC page warns that real student data must not be used.

Before real use, ICT must set restrictive Windows file permissions so only the Host service account and approved administrators can read the key, database, local snapshots, and restore staging. A local backup encryption key does not encrypt the live SQLite database, staff certificates, or TLS private key. Configure secure ACLs for those files as well. The `encryption` and `keyId` shown to TICs do not disclose the key itself.

An off-host path is only a configured destination. The service cannot determine whether it is an independent school-controlled device, network share, or approved records location. Health therefore reports `independentStorageVerified: false` even when copies succeed. Do not treat an ordinary second folder on the same device as an independent backup. ICT must approve the destinations and records retention rule. The restore route is not yet a tested school recovery procedure. Secure Windows key provisioning, host replacement, and point-in-time recovery drills remain before real student data.

## API and current limits

The restore API has only been tested with fictional snapshots on one development process. It does not yet have a completed school host replacement or point-in-time recovery drill. The encryption format has unit tests; secure Windows key provisioning, Entra sign-in, LAN conditions, off-host destinations, and host replacement recovery remain untested at school.

- `GET /api/v1/health` reports local SQLite, app-serving mode, configured listener mode, and the unverified school-LAN test state without exposing storage paths.
- The Host serves built static files on its own origin, uses the built `index.html` as the client-side route fallback, and never serves `/api/*` paths as HTML. Missing `/api/turn` relay credentials return `503`; existing PeerJS relay pairing remains dependent on its external matchmaking/TURN services.
- `/hub-admin` is the Host access and recovery page; `/settings` links to it while preserving the existing classroom backup and restore tools.
- `GET /api/v1/auth/options` reports whether Entra is configured, whether ICT has confirmed the MFA policy, and labels the local named-profile fallback as development-only.
- `POST /api/v1/auth/entra/start` begins Entra sign-in and returns an authorization URL for the browser to open as a top-level navigation. For a first profile link, include the TIC-issued invitation token.
- `GET /api/v1/auth/entra/callback` completes the authorization-code exchange, validates state and nonce through MSAL, checks tenant/object/email claims, sets the secure host session cookie, and returns the browser to `/hub-admin`.
- `GET /api/v1/backups/health` reports detailed backup health to TICs.
- `POST /api/v1/backups/run` runs a TIC-requested backup cycle and records the request/result in the Host audit log.
- TIC-only restore routes list available points, stage and verify a selected file for preview, and require a separate explicit promotion request. Promotion checks that the live revision has not changed, creates a pre-restore snapshot, updates the account snapshot in one transaction, and adds an audit event. Staging files and all backup generations are retained.
- `POST /api/v1/enroll`, `GET /api/v1/session`, and `POST /api/v1/sign-out` manage the local fallback session.
- TICs create a ten-minute, single-use Hub kiosk activation ticket with `POST /api/v1/kiosk/start`. Open the returned fragment-based link in a separate kiosk browser profile; `POST /api/v1/kiosk/activate` redeems it and sets a kiosk-only cookie. `POST /api/v1/kiosk/stop` revokes the active kiosk session and outstanding activation links. Kiosk state and movement actions are available only through the kiosk-scoped API routes.
- Destination settings support versioned arrival and final-departure prompts, with written answers or 1–5 / 1–10 ratings. The kiosk receives only the current stage's safe question configuration. It submits prompt IDs, answers, and the destination prompt version; the Host checks required answers and configuration freshness, then stores immutable question/configuration/answer/time snapshots on the Main Hub Visit. Temporary Trip start/return does not run departure prompts. Staff with an active session can issue a reasoned ten-minute, single-use override for a current student and matching destination/stage with `POST /api/v1/hub/prompt-overrides`; the Host records its staff attribution and audit event. The kiosk receives only a matching override indicator, never its reason or staff identity. A kiosk action is reported as saved only after the Host acknowledges it.
- `GET` and `PUT /api/v1/preferences` read and save only the signed-in profile's favourites. Host mode keeps these IDs outside the shared student snapshot; the browser-local app stores favourites in that browser only.
- `GET /api/v1/concerns/settings` returns the available concern routes and default. TICs can update them with `PUT /api/v1/concerns/settings`; the default policy offers TIC, All staff and Choose staff, with TIC as the default. `GET /api/v1/mail/recipients` returns the authorised staff directory needed for Choose staff. `POST /api/v1/concerns` stores a private note outside the shared account snapshot and freezes the exact recipient profile IDs, names, and roles at submission. `GET /api/v1/mail` returns only messages for the sender, selected recipients, or TIC oversight. `POST /api/v1/mail/{messageId}/read` records a recipient's read state. The shared Hub Visit contains only a `hasConcern` warning flag; it never contains the note. Non-recipients may see the operational warning but receive no note text or pop-up preview. Recipient clients poll the Host for unread messages; the pop-up is generic. Acknowledgement and external email are not implemented.
- Classroom staff can confirm physical arrival for a waiting Hub notification from Home. Students can also confirm notified arrival, sign in directly at a kiosk-enabled destination without a classroom departure timestamp, and leave through the separate Hub kiosk. A student at the Hub can start and return from one TIC-enabled Temporary Trip nested under the same Main Hub Visit. Each kiosk action is Host-acknowledged, PIN-checked when enabled, timestamped and audited. TICs may configure a student-safe kiosk confirmation and arrival chime per destination; the Host sends the message and chime choice only after saving an arrival, and uses a privacy-safe destination label when no message is set. TICs can also set a common departure/return chime, master mute and volume. The common chime is played after the kiosk records a Hub departure or Temporary Trip return, and after staff confirm the student's return to class. The Hub kiosk plays a separate notification sound for newly received classroom arrivals. Audio is optional and never affects whether a movement is recorded. TIC activation links are single-use and expire after ten minutes; staff sign-in and kiosk sessions remain separate. The kiosk receives only shortened names, safe destination labels, movement status and the sanitized Hub sound settings; it cannot read private concern notes. A Hub departure does not automatically confirm class return. Staff can withdraw a notification or mark it Did Not Arrive only before arrival. The added movement/settings fields are optional snapshot properties; kiosk ticket/session tables are added by schema v7.
- Home keeps unresolved movements visible after the active class changes, labels them for period-transition review, and warns staff before a manual class switch. The switch does not rewrite or close the Hub Visit.
- TIC-only routes manage invitations, profiles, sessions, audit events, backups, and restore. Both staff roles can read `/api/v1/state`; EAs receive a redacted account view and may write allowlisted operational fields, including validated Hub notifications, pre-arrival cancellations, and return confirmations. TICs can write the full existing Happy Hallways account snapshot.
- Snapshot writes use optimistic revision checks and SHA-256 checksums. A stale staff client may send the snapshot it originally read as `baseSnapshot`; the Host then merges independent object fields and stable-ID records. If clients changed the same field or an ordering cannot be reconciled safely, the Host returns `409` with conflict paths and leaves the saved state unchanged. A stale request without its base snapshot also returns `409`. Damaged saved state is not overwritten.
- The Host marks its served HTML so the shared app distinguishes Hub mode from the existing browser-local version. In Hub mode, teacher screens stay behind staff sign-in until a Host account is loaded. The Host account is held in memory on staff clients and writes go to SQLite; Hub mode does not write a second account copy to each browser's `localStorage`. The sidebar shows the save state, pass/kiosk notices wait for Host acknowledgement, and clients poll for updates every 2.5 seconds.
- A TIC can initialise an empty Host from the current browser account only through an explicit action. The page first downloads a JSON backup, then copies the account to the Host. The browser source remains unchanged. An unreadable local account cannot be imported.
- EA accounts can use Home and History. Setup/device pages are hidden and direct navigation is redirected. The Host also rejects EA changes outside its operational-field allowlist and omits the teacher PIN, student PINs, kiosk pairing secret, claim tokens, replaced-kiosk secrets, and Student link room code from EA responses.
- The current shared data model is still the existing Happy Hallways account snapshot, including the Hub Visit and Temporary Trip records. Concern notes and recipient read state live in separate Host tables. The broader Details, History/reporting and Mail Centre features are not implemented beyond this concern workflow. Existing records also do not yet have all required per-action staff attribution. The browser integration has not yet been exercised across multiple browsers on an actual school LAN.
- The existing PeerJS pairing and Student link implementation remains in the code and still depends on its existing external matchmaking/TURN services in some network conditions. Those paths have not been redesigned for multi-client Hub operation. The Host HTTP account path uses the school LAN once approved, but the overall app must not be described as internet-independent while those existing paths are enabled.
- LAN mode remains disabled by default. Entra integration is behind ICT configuration gates, but no Department tenant registration, Conditional Access/MFA policy, key ACL, or provider sign-in has been tested. HTTPS LAN binding remains unapproved and untested on the school network. Do not expose it to that network or load real student data.

Before any real deployment, ICT needs to register the Entra application, set and confirm the MFA policy, approve the server certificate/key storage, issue the host TLS certificate, set DNS/firewall rules, confirm the school-controlled off-host backup destination and records retention rule, and approve the recovery procedure. In plain language: “Can ICT register this app for staff sign-in, confirm staff MFA is required for it, tell us how the Windows Host should securely access its certificate key, issue a certificate for the Host name, and confirm the approved backup location and retention rule?” Keep account passwords and private keys out of chat and source control. PeerJS, STUN, and TURN are not part of this local-first Host path and require separate approval if reconsidered.
